# Zeditor v0.6.5 产品与普通用户视角评估

原始评估日期：2026-10-19。评估代码基线：HEAD `02988f9`。本次后续实施状态与验证记录见第 10 节。

## 1. 总体判断

Zeditor 已有完整的桌面 Markdown 工作台雏形，功能覆盖很广，部分能力已经具有独立吸引力。不过，目前的证据更支持“功能丰富、正在打磨的个人开发者产品”，还不足以认定已经达到成熟商业编辑器的整体质量。

现阶段最值得投入的是让已有功能形成可靠、容易理解、输出一致的日常使用流程。建议优先解决文稿恢复、外部变更保护、附件备份、编辑与导出一致性，再改善默认界面和中文编辑手感。继续增加主题、Agent 后端或小众工具，对近期产品成熟度的帮助可能较小。

这是一份产品判断，不是用户调研结论；普通用户视角是基于实际界面检查和任务走查提出的体验假设，应通过真实用户试用验证。

## 4. 产品经理视角：当前版本

### 4.1 定位应比功能列表更明确

当前同时覆盖写作、知识管理、开发者工具、AI 工作台和内容发布。对单人开发者来说，这会扩大每次发布的验证范围，也会让用户难以判断产品最适合自己做什么。

建议先以“本地优先、适合中文资料整理与写作、能够审阅 AI 修改的 Markdown 编辑器”为待验证定位。优先服务经常处理文档、撰写文章/报告、保留本地文件并需要导出分享的个人用户。技术文档是重要兼容场景。

建议用完整任务介绍产品，例如“导入资料 → 整理和写作 → 审阅 AI 建议 → 导出交付”。GitHub Actions DAG、MCP 和 Agent 高级设置保留，但收纳到相应的高级入口。

### 4.2 产品建议排序：先防止丢稿，再完善备份与交付

优先级定义：**P0** 为涉及文稿丢失或被静默覆盖的核心数据保护；**P1** 为形成可恢复、可交付的完整日常工作流；**P2** 为依据目标用户需求决定的格式扩展。当前依据来自代码与本地前端检查；标注“待桌面验证”的事项不能视为已复现的桌面故障。

| 优先级 | 已确认现状与证据边界 | 用户影响 | 建议行动 | 验收标准 |
| --- | --- | --- | --- | --- |
| P0 · 数据恢复 | 自动保存只保存有磁盘路径的已修改文档；store 中的标签内容和时间线为内存状态。浏览器重载后，未保存的无路径草稿会消失；桌面崩溃恢复尚未实测。 | 新建草稿或尚未保存的修改可能在重启后找不回来；用户也难判断能否关闭应用。 | 为未命名草稿及已命名文档的未保存修改建立本地恢复快照。启动时展示可预览的恢复清单，用户可恢复、另存为或丢弃；快照与历史版本分开保留，并设置明确的保留和清理规则。 | 在桌面版分别覆盖无路径草稿、有路径文档的未保存修改、正常退出和强制结束进程；重启后均能找到正确快照。恢复不覆盖原文件，确认丢弃后不再显示该快照。 |
| P0 · 冲突保护 | 打开已有标签时直接切回内存内容；常规保存写入当前内存内容。代码中未找到通用的文件变更监听、保存前版本检查与冲突处理流程；真实磁盘冲突待桌面验证。 | 外部编辑器、同步盘或文件恢复程序修改了同一文件时，Zeditor 可能保存旧内容并覆盖外部修改。 | 读取后记录文件版本信息；在文件变化、窗口重新聚焦和保存前检查。检测到内外两份均有修改时暂停自动保存，展示差异，允许重新载入、另存为副本或手动合并。 | 用第二个编辑器修改文件后回到 Zeditor，再分别验证手动保存和自动保存。存在冲突时不得静默覆盖，用户可以保留两侧内容并明确完成处理。 |
| P1 · 删除恢复 | 删除操作有确认提示，后端实际调用 `remove_file` / `remove_dir_all`，没有回收站步骤。 | 确认对话框无法挽回误选或之后发现的误删。 | 将普通文件与文件夹删除移入系统回收站，并提供失败提示；平台不支持时，改用 Zeditor 的可恢复暂存区。 | 删除后可在应用或系统回收站恢复；打开的标签状态正确；回收站不可用时说明恢复方式，并让用户能在删除前取消。 |
| P1 · 附件备份完整性 | 云备份任务读取并上传当前 Markdown 文件字节；本次代码检查未找到沿 `.assets` 引用同步图片/媒体的完整流程。实际跨设备恢复未测试。 | 备份的 Markdown 在另一台设备可能缺少图片和媒体，文档显示不完整。 | 明确区分“只备份 Markdown”和“完整备份文档及附件”。建议将被引用的 `.assets` 资源纳入备份清单，与文档版本一同校验、恢复和清理；保留本地优先原则。 | 在全新目录恢复一份含多个图片/媒体的文档；核对相对路径、文件哈希与离线显示。再覆盖附件缺失、重命名、删除和旧版本恢复，不留下静默断链。 |
| P1 · 导出一致性 | 预览和所见即所得共用 Markdown 管线，部分 HTML/Word 导出建立独立 MarkdownIt 实例；不同出口的一致性尚未形成完整验收。 | 预览看起来正常，导出的脚注、公式、图表、图片尺寸或 Wiki 链接却可能表现不同。 | 建立一份固定的复杂样稿和格式支持矩阵；共享渲染规则，并为无法保留的元素提供明确降级方式。分开验证 HTML、PDF、Word、长图和公众号出口。 | 每次发版生成全部目标格式，并核对公式、图表、任务列表、脚注、Wiki 链接、图片路径与尺寸；支持、降级或不支持的结果均有明确说明。 |
| P2 · 原生 Word 格式 | 当前 Word 菜单以 `.doc` 扩展名输出 HTML 兼容文档，`wrap_word_page` 返回 HTML，不是原生 `.docx`。 | Office/WPS 可打开不代表复杂样式、分页和目录可以稳定编辑或交付。 | 先根据目标用户确认原生 Word 是核心需求；如确认，再实现真正的 `.docx` 输出，并明确可编辑的内容与分页边界。保留现有兼容格式时，应在界面标明其类型与限制。 | 验证文件确为 OOXML `.docx`，并在目标 Office/WPS 环境中检查标题样式、表格、分页、目录、脚注和图表；用户可继续编辑主要内容。 |

### 4.3 让用户理解备份与同步的边界

现有 WebDAV/S3 云端备份已有版本记录、队列、失败重试和哈希校验。界面应继续明确哪些内容会上传、失败后如何重试、如何还原，以及这是按本地保存生成远端副本的备份流程。用户可能期待的双向同步涉及变更合并、删除传播、重命名和多设备并发，需要独立定义行为后再承诺。

附件完整恢复列在上表的 P1 项目中；本次代码检查确认云端队列以单个文档文件为主要备份对象，尚未确认 `.assets` 引用资源会随文档版本一并恢复。

### 4.5 功能说明与设置行为必须一致

`auto_complete` 出现在设置类型、默认值和设置开关中，但搜索前端没有找到编辑器读取并应用该开关的接入点。建议逐项审计设置，确保开关能改变对应行为；未完成的选项应隐藏或注明状态。

AI 修改确认已经有前后内容、拒绝、应用和撤销，是正确基础。但把非 `fact` 类建议统一描述为“不涉及事实核验”过于绝对，润色与翻译仍可能改动数字、时间和主体。建议改为提醒核对事实，并高亮数字、专名、引用来源变化；逐步提供真正的行内差异和分段采纳。

凭据目前随设置以明文保存，隐私政策已经披露；前端启动缓存也会序列化完整 settings。建议接入系统凭据存储，并让启动缓存仅保存非敏感外观/行为偏好。此处是明确实现边界，不是本次发现泄露事件。

## 5. 普通用户视角：当前版本

### 5.1 第一印象：统一、清楚，但仍偏工具工作台

实看明暗主题，标题、正文、代码块、侧栏的视觉语言一致。所见即所得的完整页面比源码对照更有写作空间感。已有样式基础适合渐进打磨。

主要体验问题与建议：

| 用户感受或任务 | 观察/代码依据 | 建议 |
| --- | --- | --- |
| “我只想马上写一段文字。” | 首次启动需要先选择编辑方式 | 保留说明，提供突出的“开始写作”，默认进入所见即所得；首次引导可跳过、可稍后再看 |
| “文件为什么在几处重复出现？” | 分屏两侧各有标签栏，左侧又有打开的编辑器 | 若两侧不是独立比较文档，优先一套全局标签，面板只标“编辑 / 预览”；侧栏打开列表允许默认收起 |
| “窗口小了以后太挤。” | 900px 时无页面横向溢出，但源码/预览各约 294px；1200px 下长标题已换行 | 根据正文最小可用宽度收起辅助侧栏或给出切换单栏入口；保留用户选择并能恢复 |
| “字偏小，长时间读写累。” | 默认正文 14px、行高 1.4、UI 13px，截图正文偏密 | 提供标准/舒适/紧凑预设；中文写作可试 16–17px、1.6–1.75 行高，经用户试用确定默认值 |
| “底部这些状态都需要看吗？” | 同时出现模式、AI、校对、伴写、云服务、字数、编码等 | 默认突出保存状态、字数和当前模式，其他按启用状态或异常出现 |
| “设置里有些词我不懂。” | 有毫秒、EditContext、图床、MCP 等术语，11 个分类 | 自动保存显示“30 秒”；输入引擎放进高级/故障排查；新增设置搜索，给服务类选项补简单用途说明 |
| “我先贴截图，为什么还要先保存？” | `requireDocumentPath` 要求文档已有磁盘路径 | 先接入草稿附件暂存，另存为后迁移到 `.assets`，处理好失败和路径回写 |
| “怎么把笔记交给其他软件？” | Wiki/脚注存在已公开的导出与语法限制 | 明确兼容级别，支持标准 Markdown 链接降级和完整脚注排版，再决定是否扩展知识库功能 |

排版建议是审美与阅读体验判断，不是所有用户的统一偏好。不要通过增加更多主题来替代默认排版质量。

### 5.2 普通用户未来最关心的顺序

1. 写下的内容不会无故消失，写错、误删可以找回。
2. 中文输入、选区、撤销、列表与表格的手感可预期。
3. 保存、备份、导出完成了什么一目了然，失败后有可操作出口。
4. 导出的文档能直接交付，换电脑后图片仍能看到。
5. AI 能帮忙，而且修改范围、发送内容和撤销方式清楚。

建议邀请 5–8 位目标用户，分别尝试新建图文笔记、导入资料、修改表格、审阅 AI 建议、导出和恢复。记录任务完成率、求助点和时间；本文没有真实用户样本，不宜据此宣称某个界面方案一定更好。

## 6. 性能：已有优化，但仍需完整基准

已确认代码采取按需加载、细粒度状态订阅、延迟统计、所见即所得单块增量解析、分批渲染、图表可见时加载。选择 Tauri/Rust 和采用这些优化，都是合理基础，但不能直接推导出实际占用更低或优于竞品。

本次生产前端单轮测量如下，均在应用已启动后添加内存文档，启用 CPU Profiler：

| 样稿 | 源码对照首次可见 / 完整就绪 | 所见即所得首次可见 / 完整就绪 |
| --- | --- | --- |
| 260 段文字，261 块 | 149 / 176ms | 118 / 492ms |
| 120 组标题、段落、表格、代码，481 块 | 261 / 291ms | 81 / 1025ms |
| 项目已有交接文档，61 块 | 441 / 481ms | 244 / 415ms |

AI 面板拖动这一轮 P95 帧间隔约为分屏 66.8ms、所见即所得 33.3ms。另一个现有显示回归中，300 段落行宽拖动的 P95 分别约 16.9ms 和 33.3ms，两种模式均有约 133ms 的最大帧间隔。不同文档、控件、采样方式之间不能直接比较；这些数字说明仍有长帧，不能宣称全程 60fps。

纯解析脚本处理 64,888 字符、12,000 块的中位数约 39.5ms；它只说明分块算法的一部分开销，不代表长文档完整编辑性能。

原有打开基准脚本首次因混合换行被 Monaco 规范化后不再逐字相等而超时；本次仅在忽略目录中的副本统一样稿换行为 LF，并用当前预览标题确认就绪后完成观测。不能把原脚本的超时直接计为产品打不开文档，也不能把副本结果称为原脚本原样通过。没有修改仓库原脚本。

目前仍需重点测量：

- 安装版冷启动到能输入，而非页面加载或 Logo 出现；
- 中文输入到绘制的 P95/P99 延迟、快速删除与撤销；
- 1 万/10 万/50 万中文字，密集表格、公式和图片；
- 1000/10000 文件工作区搜索与反向链接，超预算时应有可见提示；
- 20/50 标签驻留内存、关闭回收、后台 CPU 和电池影响。

建议先固定参考机器与样稿，再定预算。例如普通文档输入 P95 <50ms、典型文档切换 <200ms、超大文档支持明确的降级方式；这些是待校准目标，不是当前达标声明。

源码上下一处值得剖析的是 `Preview.tsx:101` 的全文 HTML 重建，`useDeferredValue` 改变调度但并不自动消除完整解析与 DOM 替换。先看输入和滚动剖析，再决定增量更新、Worker 或视口渲染，不应立即重写内核。

## 7. 如何对标成熟产品

只选择与核心任务对应的维度，避免把每个竞品的全部功能都搬进路线图：

| 产品 | 官方资料确认的参考方向 | 对 Zeditor 的启发 |
| --- | --- | --- |
| [Typora](https://typora.io/) | 连贯的实时预览、文件与大纲、专注/打字机、主题与导出 | 优先学习编辑的连贯性和默认排版 |
| [Obsidian](https://obsidian.md/) | 本地文件、链接组织、插件与同步/发布 | 如要进入知识管理，需补齐链接维护和工作区能力，不能仅以支持 `[[链接]]` 宣称完整兼容 |
| [VS Code Markdown](https://code.visualstudio.com/docs/languages/markdown) | 大纲、路径/标题补全、本地链接校验与 Markdown 工作流 | 参考链接可维护性、键盘效率与错误反馈 |
| [MarkText](https://github.com/marktext/marktext) | 开源实时预览编辑器，多种编辑模式和主题 | 参考开源实现和交互；本次未核验维护活跃度，不据此作维护状态判断 |

本次没有安装并用同一套数据测量上述产品，不能给出“Zeditor 已超过/落后多少”的客观分数。最有机会的组合是本地中文写作、资料转换、可控 AI 与可靠交付，这仍需目标用户验证。

## 8. 建议的未来推进顺序

按验收条件推进，版本名称仅为建议，不是开发时间承诺。

| 阶段 | 优先工作 | 可检查的完成标准 |
| --- | --- | --- |
| 第一阶段：可靠使用 | 草稿/会话/本地历史持久化；外部变更冲突；回收站；备份范围说明和附件恢复 | 强杀后能找回草稿；外部修改不会被无提示覆盖；误删可恢复；全新目录恢复图文可离线阅读 |
| 第二阶段：写得舒服 | 一套清晰标签；窄窗策略；舒适排版预设；设置搜索与高级项收纳；中文输入与撤销回归 | 目标用户无需帮助完成写作/表格/插图任务；100%–200% 缩放不遮挡关键操作；跨模式编辑结果与撤销可预期 |
| 第三阶段：交付与特色 | 统一导出语义；根据定位建设原生 docx；AI 差异、事实变化提醒与上下文说明；系统凭据存储 | 一套复杂样稿在指定 Office/WPS/PDF 阅读器验收；AI 修改可分段确认和撤销；凭据不进入普通配置/启动缓存 |
| 1.0 准备 | 持续集成、固定性能预算、跨平台安装验收、签名/公证与已知限制 | 连续若干候选版通过同一套核心任务；没有已知丢稿/静默覆盖问题；性能结果可复现；发行说明与实际产物一致 |

维护方面，现有测试包含行为测试，也包含读取源码字符串的接线/结构断言。保留有价值的约束，但不要以总数量代替真实用户流程覆盖。当前构建质量门槛主要在发版标签触发，建议补普通 PR 的轻量检查，以及固定的浏览器编辑流程回归。

App、Editor、所见即所得会话和 Rust commands 文件规模较大。无需全面重构；每次修改相关功能时逐步抽离文件生命周期、导出、快捷键等职责，并由行为回归保护。维护能力、恢复能力和默认体验，应先于插件市场、移动端、实时协作、大型知识图谱和更多 AI 供应商扩张。

## 10. 后续实施状态（2026-10-19）

按 §4.2 的优先级实施；下列状态更新于 2026-10-20。前九节保留初始代码基线的评估，当前功能与验证结果以本节为准。

### 已实施

- **草稿恢复快照**：保存到独立的应用配置文件，与用户可见的时间线历史分开。桌面启动后可预览、恢复到新标签、另存或丢弃；正常保存和用户明确放弃时清理对应快照。当前上限为每条 2 MiB、最多 20 条、总计 32 MiB，7 天过期。
- **外部文件冲突保护**：打开时记录文件字节长度和 SHA-256；切换标签、窗口重新获得焦点和保存时重新比较。检测到磁盘改动后暂停该标签自动保存，展示本地与磁盘内容；可以另存、重载、打开磁盘副本，或二次确认后覆盖。文件在外部删除时保留本地内容并允许另存。
- **导出基础渲染一致性**：主菜单 HTML/PDF、PDF 对话框、PNG 与公众号导出改用 `renderMarkdownToHtml`；Word 使用同一 Markdown 解析器的 token 生成 OOXML。公式、脚注、任务列表、图片语法和 Wiki 链接共用基础解析规则，各格式的呈现能力仍有差异。
- **系统回收站删除与恢复**：Windows 优先使用明确的回收标志；Windows/Linux 按系统项目 ID 记录和恢复。系统不可用时只尝试同卷原子移动到应用恢复区，失败则取消删除，不降级为永久删除。资源管理器新增“回收站与恢复”；同名目标拒绝覆盖。删除文件夹后，未保存的子文档保留为草稿；保存与回收串行执行，防止排队保存重新创建已删除文件。macOS 的系统废纸篓项目明确提示在访达恢复。
- **附件随云备份恢复**：WebDAV/S3 将引用的同级 `.assets` 文件与每个文档版本关联，记录相对路径、大小、SHA-256 和编码。仅修改附件也产生新版本；全部资源上传成功后才发布清单。恢复前核验文档引用与清单一致、全部哈希正确，再写入独立新文件夹。旧版备份明确标为“仅文档”。范围外的本地图片、媒体及下载附件会报错，网络 URL 不会下载；详见云备份指南。
- **原生 `.docx`**：Word 菜单生成真正的 OOXML ZIP，支持可编辑正文、标题样式、列表、表格、图片、超链接、原生脚注、目录域和页码域。图片读取失败中止导出；SVG/WebP/AVIF 转 PNG。公式保留精确 TeX，图表保留源码，并在保存后提示格式降级；不宣称与屏幕预览完全一致。
- **本机 Rust 工具链修复**：补齐 stable 1.95.0 缺失的 `rustc_driver` DLL。下载包与本机原有官方清单 SHA-256 一致，仅恢复缺失文件，未更新 Rust 版本。另安装匹配的 rustfmt，以及原先缺失的 Microsoft C++ Build Tools 与 Windows SDK。修复记录位于 `test-output/rust-repair-record.json`。
